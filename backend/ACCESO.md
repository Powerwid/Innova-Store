# Autenticación y control de acceso

El backend usa JWT en cookies `HttpOnly`. `POST /api/auth/login` recibe `correo` y `contrasena`, establece `access_token` (2 horas) y `refresh_token` (7 días), y devuelve solo los datos básicos del usuario. Ambos JWT usan `JWT_SECRET`; el campo `tipo` impide usar uno en lugar del otro. La estrategia JWT lee `access_token` desde las cookies; no lee el encabezado `Authorization`. Cuando el acceso expira, la siguiente petición protegida usa automáticamente la cookie de renovación, continúa la operación y recibe una nueva cookie de acceso. No se renueva en cada petición mientras el acceso siga vigente. `POST /api/auth/refresh` también permite renovar de forma explícita. `POST /api/auth/logout` borra ambas cookies. `GET /api/auth/me` devuelve el usuario, su único rol, los permisos heredados de ese rol y sus sucursales asignadas. `PATCH /api/auth/contrasena` cambia la contraseña propia y exige la anterior.

Las cookies usan `SameSite=Lax`; en producción también usan `Secure`. La cookie de renovación se envía a las rutas `/api` para permitir la renovación automática. En desarrollo, Vite sirve Vue en `http://localhost:5173` y reenvía `/api` al backend; el frontend debe usar rutas relativas como `/api/auth/me`. En producción Nest sirve el frontend compilado y `/api` bajo el mismo origen. En una colección de pruebas basta `base_url=http://localhost:3000/api`: el cliente HTTP debe conservar las cookies después del login; no necesita una variable `access_token`.

El cierre de sesión borra las cookies del navegador. Los JWT de renovación ya emitidos no se almacenan ni revocan en el servidor, por lo que un token copiado antes del cierre seguirá siendo válido hasta que expire. La estrategia consulta el estado del usuario al renovar y rechaza cuentas inactivas.

Todas las rutas requieren autenticación salvo las marcadas expresamente con `@Public()`. Además, una ruta autenticada debe declarar una política: `@RequierePermiso('CODIGO')`, `@RequiereRol('NOMBRE')`, `@SoloSuperadmin()` o `@Autenticado()`. El acceso sin política se deniega. `EstadoGuard` exige por defecto el estado `ACTIVO`; `@EstadosPermitidos(...)` permite declarar otros estados cuando una operación lo necesite.

El rol y sus permisos se resuelven desde MySQL en cada solicitud. Cada usuario tiene exactamente un rol obligatorio y hereda exclusivamente los permisos asociados a ese rol. `SUPERADMIN` recibe mediante los seeders todos los permisos definidos internamente; no existe un atajo en el guard que ignore `roles_permisos`. Solo ese rol puede usar las rutas de administración de roles y permisos mediante `@SoloSuperadmin()`. `RolesGuard` admite nombres de rol dinámicos, pero las operaciones normales deben preferir permisos.

La gestión de acceso vive dentro de `UsuariosModule`:

- `GET/POST /api/roles`, `PATCH /api/roles/:idRol` y `DELETE /api/roles/:idRol` para consultar, crear, editar y eliminar roles administrables.
- `PATCH /api/usuarios/:idUsuario/rol` para reemplazar el único rol de un usuario.
- `GET /api/permisos` para obtener el catálogo interno con etiqueta, módulo y orden.
- `PUT /api/roles/:idRol/permisos` con `{ "idsPermisos": [] }` para reemplazar atómicamente todos los permisos de un rol. También se conservan las rutas individuales `POST /api/roles/:idRol/permisos` y `DELETE /api/roles/:idRol/permisos/:idPermiso`.

`SUPERADMIN` no aparece entre los roles administrables y no puede renombrarse, desactivarse, eliminarse ni recibir cambios manuales de permisos. No se puede cambiar el rol del último superadministrador activo ni el rol propio desde la ruta administrativa. Un rol con usuarios asignados no puede eliminarse. La edición y los cambios de estado generales tampoco pueden actuar sobre una cuenta superadmin. `PATCH /api/usuarios/:id` permite actualizar datos y habilitar o deshabilitar con `{ "estado": "ACTIVO" }` o `{ "estado": "INACTIVO" }`; no borra físicamente al usuario. Para datos se exige `USUARIOS_EDITAR`, para activar `USUARIOS_ACTIVAR` y para desactivar `USUARIOS_DESACTIVAR`; una petición que combina cambios necesita todos los permisos correspondientes. `BLOQUEADO` no se cambia desde esta ruta. Un rol desactivado se reactiva con `PATCH /api/roles/:idRol` y `{ "activo": true }` (solo SUPERADMIN).

Los códigos de permiso se añaden exclusivamente al enum `src/common/enums/permiso-sistema.enum.ts` y al catálogo `src/common/constants/permisos-sistema.ts`; la API no permite crear permisos. Al ejecutar los seeders, la tabla `permisos` se sincroniza con ese catálogo y `SUPERADMIN` recibe exactamente todos los permisos vigentes. Las asignaciones de los demás roles no se reescriben y quedan bajo control del superadministrador. Los usuarios creados por la API deben indicar un `idRol` activo y no pueden crearse directamente como `SUPERADMIN`.

Para iniciar la base, configure las variables de `.env.example`, aplique las migraciones de Prisma y ejecute el seed. No coloque secretos reales en el repositorio.
