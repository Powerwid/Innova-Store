# Autenticación y control de acceso

El backend usa JWT en cookies `HttpOnly`. `POST /api/auth/login` recibe `correo` y `contrasena`, establece `access_token` (2 horas) y `refresh_token` (7 días), y devuelve solo los datos básicos del usuario. Ambos JWT usan `JWT_SECRET`; el campo `tipo` impide usar uno en lugar del otro. La estrategia JWT lee `access_token` desde las cookies; no lee el encabezado `Authorization`. Cuando el acceso expira, la siguiente petición protegida usa automáticamente la cookie de renovación, continúa la operación y recibe una nueva cookie de acceso. No se renueva en cada petición mientras el acceso siga vigente. `POST /api/auth/refresh` también permite renovar de forma explícita. `POST /api/auth/logout` borra ambas cookies. `GET /api/auth/me` devuelve el usuario, su único rol, los permisos heredados de ese rol y sus sucursales: las asignadas para cuentas normales y todas las activas para `SUPERADMIN`. `PATCH /api/auth/contrasena` cambia la contraseña propia y exige la anterior.

Las cookies usan `SameSite=Lax`; en producción también usan `Secure`. La cookie de renovación se envía a las rutas `/api` para permitir la renovación automática. En desarrollo, Vite sirve Vue en `http://localhost:5173` y reenvía `/api` al backend; el frontend debe usar rutas relativas como `/api/auth/me`. En producción Nest sirve el frontend compilado y `/api` bajo el mismo origen. En una colección de pruebas basta `base_url=http://localhost:3000/api`: el cliente HTTP debe conservar las cookies después del login; no necesita una variable `access_token`.

El cierre de sesión borra las cookies del navegador. Los JWT de renovación ya emitidos no se almacenan ni revocan en el servidor, por lo que un token copiado antes del cierre seguirá siendo válido hasta que expire. La estrategia consulta el estado del usuario al renovar y rechaza cuentas inactivas.

Todas las rutas requieren autenticación salvo las marcadas expresamente con `@Public()`. Además, una ruta autenticada debe declarar una política: `@RequierePermiso('CODIGO')`, `@RequiereRol('NOMBRE')`, `@SoloSuperadmin()` o `@Autenticado()`. El acceso sin política se deniega. `EstadoGuard` exige por defecto el estado `ACTIVO`; `@EstadosPermitidos(...)` permite declarar otros estados cuando una operación lo necesite.

El rol y sus permisos se resuelven desde MySQL en cada solicitud. Cada usuario tiene exactamente un rol obligatorio y hereda exclusivamente los permisos asociados a ese rol. `SUPERADMIN` recibe mediante los seeders todos los permisos definidos internamente; no existe un atajo en el guard que ignore `roles_permisos`. Solo ese rol puede usar las rutas de administración de roles y permisos mediante `@SoloSuperadmin()`. `RolesGuard` admite nombres de rol dinámicos, pero las operaciones normales deben preferir permisos.

La gestión de acceso vive dentro de `UsuariosModule`:

- `GET/POST /api/roles` y `DELETE /api/roles/:idRol` para consultar, crear y eliminar roles administrables.
- `PATCH /api/usuarios/:id` permite actualizar al usuario y, opcionalmente, reemplazar su único rol enviando `idRol` en el mismo JSON.
- `GET /api/permisos` para obtener el catálogo interno con etiqueta, módulo y orden.
- `PUT /api/roles/:idRol/permisos` con `{ "idsPermisos": [] }` para reemplazar atómicamente todos los permisos de un rol.

La administración de medios de pago usa `GET/POST /api/medios-pago` y `PATCH/DELETE /api/medios-pago/:id`. Cada operación exige su permiso `MEDIOS_PAGO_VER`, `MEDIOS_PAGO_CREAR`, `MEDIOS_PAGO_EDITAR` o `MEDIOS_PAGO_ELIMINAR`. El catálogo se inicia con Efectivo, Tarjeta de crédito/débito, Yape, Plin y Fraccionado. La tabla `medios_pago` contiene únicamente identificador y nombre.

`SUPERADMIN` no aparece entre los roles administrables y no puede eliminarse ni recibir cambios manuales de permisos. Los roles no tienen estado ni ruta de edición. No se puede cambiar el rol del último superadministrador activo ni modificar el usuario propio desde la ruta administrativa. Un rol con usuarios asignados no puede eliminarse. La edición y los cambios de estado generales tampoco pueden actuar sobre una cuenta superadmin. `PATCH /api/usuarios/:id` concentra la actualización: acepta datos, `idRol` y `{ "estado": "ACTIVO" }` o `{ "estado": "INACTIVO" }`; no borra físicamente al usuario. Cambiar `idRol` exige ser `SUPERADMIN`; para datos se exige `USUARIOS_EDITAR`, para activar `USUARIOS_ACTIVAR` y para desactivar `USUARIOS_DESACTIVAR`. Una petición que combina cambios necesita todas las autorizaciones correspondientes. `BLOQUEADO` no se cambia desde esta ruta.

Los códigos de permiso se añaden exclusivamente al enum `src/common/enums/permiso-sistema.enum.ts` y al catálogo `src/common/constants/permisos-sistema.ts`; la API no permite crear permisos. Al ejecutar los seeders, la tabla `permisos` se sincroniza con ese catálogo y `SUPERADMIN` recibe exactamente todos los permisos vigentes. Las asignaciones de los demás roles no se reescriben y quedan bajo control del superadministrador. Los usuarios creados por la API deben indicar un `idRol` existente y no pueden crearse directamente como `SUPERADMIN`. La consulta de documentos requiere sesión, pero no un permiso propio.

Para iniciar la base, configure las variables de `.env.example`, aplique las migraciones de Prisma y ejecute el seed. `ADMIN_CORREO` y `ADMIN_CONTRASENA` crean una cuenta ADMIN asociada a «Sucursal Principal»; el seeder no reescribe su contraseña ni permisos en ejecuciones posteriores. El superadministrador asigna los permisos del rol ADMIN desde la administración. No coloque secretos reales en el repositorio.
